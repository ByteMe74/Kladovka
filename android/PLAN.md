# Состояние и план Kladovka

Проверено по коду, а не по намерениям. Подробности по безопасности — в
[`IMPROVEMENTS.md`](IMPROVEMENTS.md), по сборке десктопа — в
[`../kladovka-desktop/README.md`](../kladovka-desktop/README.md).

## Что сделано

### Android — `kladovka/`

Kotlin, Jetpack Compose, Room-схема версии 5.

- `ui/AppViewModel.kt` — ViewModel с логикой синхронизации
- `data/Repository.kt` — работа с Room + сетевые вызовы
- `data/AppDatabase.kt`, `data/Daos.kt`, `data/Entities.kt` — схема
- `ui/MainScreen.kt` — 5 вкладок: Места, Стеллажи, Полки, Контейнеры, Вещи
- Экраны редактирования всех пяти сущностей, `SyncDialog.kt`
- `android:usesCleartextTraffic` отключён — приложение ходит только по HTTPS

### Desktop — `kladovka-desktop/`

Порт Android-версии на **Compose Desktop**. Первоначальный план (Tauri + Rust +
React) отменён: общий код на Kotlin даёт паритет с телефоном без написания
второго UI, а база `kladovka.db` переносится между ПК и телефоном без
конвертации.

- Слой данных (`SqliteDatabase`, `ApiClient`, `Entities`, `Backup`) переписан
  под реальный SQLite и контракт `api.php`
- Иконки вкладок, значок приложения, счётчики — перенесены с Android
- **`gradle singleExe`** → `build\dist\Kladovka.exe`, один самодостаточный
  файл: Java не нужна ни при сборке у пользователя, ни при запуске
- Размер: 134,5 → 86,8 МБ (отсечены чужие native-библиотеки sqlite и
  неиспользуемые material-иконки; обе операции закрыты проверками в сборке)

### Сервер — `kladovka/api.php`

961 строка. Эндпоинты: `login`, `register`, `import`, `export`, `share`,
`unshare`, `profile`, `latestApk`, `upload_photo`, `logout`, `confirm`.
Rate-limiting есть для входа и регистрации.

### Веб — `kladovka/`

Обслуживается на сервере как `index.php` и `cabinet/index.php` — эти два файла и
есть источник истины. Раньше в репозитории лежали копии `landing-index.php` и
`cabinet-index.php`, которые сервер не отдавал: правки лендинга до прода не
доходили, а вместе с ними терялись CSRF-защита формы входа и правки кабинета.
Копии удалены — одна страница, один источник.

- `index.php` — лендинг. Главная кнопка ведёт на `download-handler.php`, который
  подбирает файл по ОС посетителя; рядом остались прямые ссылки на APK и, если
  сборка выложена на сервер, на EXE
- `cabinet-index.php` — кабинет (на сервере кладётся в `cabinet/index.php`)
- `download-handler.php` — раздача сборки под ОС. По умолчанию отвечает 302 на
  сам файл, поэтому вешается на `href` без JS; `?format=json` отдаёт
  `versionCode`/`versionName`/`url`/`md5`/`size` в том же формате, что и
  `api.php?action=latestApk`. Если сборки под ОС посетителя на сервере нет,
  отдаёт APK и честно помечает подмену заголовком `X-Kladovka-Served`

Поиск файла во всех четырёх PHP идёт перебором каталога регуляркой, а не через
`glob`: glob в PHP регистрозависим на всех платформах, включая Windows, и шаблон
`Kladovka-*.apk` не находит лежащий в репозитории `kladovka-v1.2.apk`. Проверено
на живом сервере — `api.php?action=latestApk` отвечал 404, а кнопка «Приложение»
в кабинете не появлялась вовсе. Версия сравнивается как `(major, minor)` из
имени файла — перезалитый старый APK не должен снова стать «актуальным» — и
правило обязано совпадать везде, иначе ссылки на разные поверхности разойдутся
версиями. `scandir()` везде закрыт проверкой `is_dir()`: без неё Warning уходит
прямо в ответ и ломает заголовки.

Но сертификат самоподписанный, Windows ему не доверяет, и щиток «Неизвестный издатель» остаётся: видимой пользы нет, а файл подписанным выглядит. Нужен настоящий сертификат (OV/EV) |

Самообновление exe не в списке и не будет: приложение портативное, запущенный
файл изнутри себя не заменить. Оно проверяет `latestExe` и открывает ссылку,
дальше человек закрывает программу и меняет файл руками.

## Проверки, встроенные в сборку десктопа

- `SingleExe verify` — SHA-256 каждой из 171 записи payload сверяется с
  исходником после упаковки
- `checkIcons` — каждая иконка, на которую ссылаются исходники, плюс шесть,
  которые material3 зовёт изнутри, грузится из готового jar и должна дать
  непустой вектор
- `slimUberJar` — падает, если в отжатом jar не нашлась ни одна ожидаемая
  иконка
- `:shared:test` — 20 тестов (`SqliteDatabaseTest` + `BackupTest`)

## Закрыто 3 октября 2026

- Пункт 2 про токены: отзыв входа сделан без ломки старых выданных токенов.
  Таблица `revoked_users`, `logout` отзывает вход пользователя, `userIdForToken`
  пропускает отозванных, новый вход снимает отзыв. Прежний `logout` был
  заглушкой: кабинет писал, что отзывает токен, а `api.php` отвечал `ok` и не
  отзывал ничего — выход стирал сессию в браузере, а доступ оставался выданным.
  Обработка 401 появилась в обоих приложениях.
- Кнопка «Выйти» в Android (не было вовсе) и в десктопе.
- Адрес сервера убран из интерфейса обоих приложений; в Android он теперь
  игнорируется и в настройках, где мог остаться от прежней версии.
- Скриншоты на лендинге (были 403), отдельный публичный `/screens/`.
- Ключ подписи Android утерян — сгенерирован новый, отпечаток
  `9F:08:8D:20…`; копии в профиле, `~/Documents` и Nextcloud.
  Из-за смены подписи 1.47 не встаёт поверх 1.46: на лендинг выведено
  предупреждение с порядком действий, сохраняющим данные.
- Автообновление на десктопе: `latestExe` на сервере, версия приложения в
  classpath из `appVersion`, значок в шапке при наличии обновления.
- Правило разбора имён сборок ужесточено во всех четырёх PHP: `Kladovka-v1.0-old.apk`
  раньше проходил как 110 и оказывался свежее `v1.10`. Теперь имя строго
  `Kladovka-v<major>.<minor>.<ext>`, а при равной версии решает каталог, а не
  дата файла.
- Пункт 1 (пароль админа) закрыт: пароль на сервере другой, проверено сравнением
  хеша и попыткой входа. Подробности — `IMPROVEMENTS.md`.

## Проверено 3 октября 2026

Аудит изоляции данных и раздачи файлов на двух пользователях (Иван и Пётр) против
живого PHP 8.2 — дыр не нашлось:

- Пётр не видит склад Ивана; подстановка чужого `ownerId` в `import`
  игнорируется, пустой имп��рт не удаляет чужие записи;
- `unshare` Пети не отзывает доступ, который ему не выдавали; шаринг самому
  себе и несуществующему логину отклоняется;
- `download-handler.php` игнорирует `ext=`, `file=`, `format=` и прочее в
  query: отдаёт только сборку, перебор 12 вариантов не дал ничего;
- `data/`, `app/`, `.git`, `server-config.php` наружу не отдаются (403/404);
- токен принимается только заголовком, в URL не попадает.

Что осталось осознанным решением, а не дырой: `/photos/<файл>` отдаётся без
токена — ссылки на фото должны работать в веб-кабинете и в сообщениях. Имя
файла выводится из его содержимого (`m-<md5>`) либо содержит 12 случайных байт,
поэтому подобрать чужое фото, не имея его самого, нельзя.
